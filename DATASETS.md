# Datasets

This repository releases the datasets generated by the data-construction pipeline used in the paper. All datasets are derived artifacts: the underlying corpora (The Pile, FineWeb) and the Pythia tokenizer are *not* redistributed here; see [`NOTICE`](NOTICE) for upstream attributions.

## Overview

| Dataset family                       | Path                                  | Purpose                                                                   |
|--------------------------------------|---------------------------------------|---------------------------------------------------------------------------|
| Pile token frequency table           | `pythia_data/pile_frequencies/`       | Per-token corpus counts over The Pile, indexed by the Pythia BPE vocab.   |
| Frequency profile                    | `pythia_data/frequency_profile/`      | Summary statistics of the log-frequency distribution over `word_en` tokens. |
| Band design                          | `pythia_data/band_design/`            | The chosen four-band partition of the `word_en` vocabulary by log-frequency. |
| Token pools (raw, validated)         | `pythia_data/token_pools{,_validated}/` | Per-band token pools, before and after FineWeb-based validation.        |
| LSC token pools (matched, unmatched) | `LSC_data/lsc_token_pools/`           | Length-matched and unmatched token pools used by the LSC generator.       |
| LSC sequences (main task)            | `LSC_data/datasets/`                  | Literal Sequence Copying inputs for circuit discovery and evaluation.     |
| LSC sequences (positive controls)    | `LSC_data/reverse_lsc/`               | Reverse-copy and zero-distractor variants used in the positive-control appendix. |

Each subdirectory described below contains a generator script alongside the artifact, so every file is reproducible from the upstream Pythia tokenizer + The Pile.

---

## 1. Pile token frequencies — `pythia_data/pile_frequencies/`

Per-Pythia-token occurrence counts over The Pile.

| File                              | Format        | Description                                                                                      |
|-----------------------------------|---------------|--------------------------------------------------------------------------------------------------|
| `merged_token_frequencies.csv`    | CSV, UTF-8    | One row per token in the Pythia vocabulary. Columns: `token_id` (int), `token_string` (raw BPE piece, includes the `Ġ` space prefix), `count` (int). |
| `merged_token_frequencies.tsv`    | TSV, UTF-8    | Identical content, tab-separated.                                                                |
| `merged_stats.json`               | JSON          | Aggregate corpus statistics (total tokens, vocab coverage, top-K, special tokens).               |
| `special_tokens_analysis.json`    | JSON          | Counts and labels for special tokens (BOS, EOS, padding, byte-level pieces).                     |
| `special_tokens_report.txt`       | plain text    | Human-readable summary of the same.                                                              |

## 2. Frequency profile — `pythia_data/frequency_profile/`

Distributional summary of the log-frequency over `word_en` tokens (English orthographic words with a leading space).

| File                          | Format | Description                                                            |
|-------------------------------|--------|------------------------------------------------------------------------|
| `frequency_profile.json`      | JSON   | Quantiles, modality test, tail thresholds, breakpoints.                |
| `frequency_profile_report.txt`| text   | Markdown-ready report of the same.                                     |
| `fig_breaks.png`, `fig_modality.png`, `fig_shape.png`, `fig_tails.png` | PNG | Diagnostic plots used to pick the four-band partition. |

## 3. Band design — `pythia_data/band_design/`

The chosen partition of the `word_en` vocabulary into four log-frequency bands plus a frequency-weighted `control` band.

| File                      | Format | Description                                                                                  |
|---------------------------|--------|----------------------------------------------------------------------------------------------|
| `final_bands.json`        | JSON   | Top-level keys: `description`, `chosen_k` (=4), `band_width` (log-freq units), `freq_ratio_per_band`, `core_range` `[lo, hi]`, `bands` (per-band log-freq edges, center, ratio, member token IDs/strings), `summary`. |
| `band_schemes.json`       | JSON   | Candidate partitions over `k ∈ {3..7}` considered during sweep, with the chosen one flagged. |
| `band_scheme_report.txt`  | text   | Human-readable comparison of the candidate partitions and the chosen scheme.                  |
| `fig_band_schemes.png`    | PNG    | Visualisation of the candidate band schemes over the log-frequency density.                   |

## 4. Token pools — `pythia_data/token_pools/` and `pythia_data/token_pools_validated/`

Per-band pools of `word_en` tokens drawn from the Pythia vocab.

- `pool_<band>.json` (raw): all tokens whose log-frequency falls in a given band, before FineWeb validation.
- `token_pools_validated/pool_validated_<band>.json`: same tokens after a FineWeb-based check that the BPE piece behaves as an isolatable English word in natural text.

Per token, each record contains: `token_id`, `token_string` (with `Ġ` prefix), `content_text` (without the prefix), `log_frequency`, `has_space_prefix`, `token_label` (`word_en`), `capitalization`, `n_content_chars`, `is_ascii`, `primary_script`, `freq_per_million`, `raw_count`, `mixed_subtype`, `is_single_token_no_space`, `is_single_token_with_space`, `fineweb_signal` (`WORD` / `SUBWORD` / etc.), `fineweb_confidence`, `substring_to_word_ratio`.

Bands available: `bottom_tail`, `low`, `medium`, `high`, `very_high`, `top_tail`, `control`.

## 5. LSC token pools — `LSC_data/lsc_token_pools/`

Per-band token pools restricted to the constraints required by the LSC generator (length-matched and unmatched variants).

Layout:

```text
LSC_data/lsc_token_pools/
├── matched/
│   ├── lsc_pool_low.json
│   ├── lsc_pool_medium.json
│   ├── lsc_pool_high.json
│   ├── lsc_pool_very_high.json
│   └── lsc_pool_control.json
├── unmatched/        (same five files; no character-length matching applied)
└── lsc_pool_summary.json
```

Each `lsc_pool_<band>.json` top-level keys: `band_name`, `band_type` (`core` / `baseline`), `log_freq_range`, `n_tokens`, `matching` (method, filters, `n_per_band`, `lengths_matched`, `tokens_per_length`), `capitalization`, `band_index`, `center`, `freq_ratio`, `log_freq_stats` (`min`, `max`, `mean`, `median`, `std`), and `tokens` (list of per-token records with the same schema as §4).

The `matched/` variant fixes the per-token character length distribution across bands so that band identity cannot be inferred from sequence length alone; `unmatched/` does not apply this matching and is provided for ablation.

## 6. LSC sequences — `LSC_data/datasets/`

The primary task data: Literal Sequence Copying inputs at the token-id level.

Layout:

```text
LSC_data/datasets/
├── matched/
│   ├── draw_1/    ├── control/  {train,val,test}.json
│   │              ├── low/      {train,val,test}.json
│   │              ├── medium/   ...
│   │              ├── high/     ...
│   │              └── very_high/...
│   ├── draw_2/    (same shape, different random seed)
│   └── draw_3/    (same shape, different random seed)
└── unmatched/     (same shape; uses the unmatched pools from §5)
```

`{train, val, test}.json` schema (top-level dict):

| Key                  | Type    | Description                                                                                       |
|----------------------|---------|---------------------------------------------------------------------------------------------------|
| `task`               | str     | `"LSC"`                                                                                           |
| `variant`            | str     | `"matched"` or `"unmatched"`                                                                      |
| `draw`               | int     | `1`, `2`, or `3` (independent random extractions per band).                                       |
| `master_seed`        | int     | `42`. Per-example seeds are derived from this.                                                    |
| `band`               | str     | `control` / `low` / `medium` / `high` / `very_high`.                                              |
| `band_type`          | str     | `baseline` (control) or `core`.                                                                   |
| `split`              | str     | `train` / `val` / `test`.                                                                         |
| `log_freq_range`     | [lo,hi] | Log-frequency range for the band.                                                                 |
| `sequence_structure` | dict    | `format` = `"[S1..S5][D1..D10][S1..S5]"`, `n_source` = 5, `n_distract` = 10, `total_len` = 21, `bos_included` = false, `prediction_position` = 20. |
| `n_examples`         | int     | Number of examples in this split. Sizes used in the paper: train = 1050, val = 225, test = 225 per band per draw (70 / 15 / 15 split of 1500). |
| `token_construction` | str     | Reminder that examples are *token IDs*, not text; BOS is not prepended (set `prepend_bos=True` at inference if your loader needs it). |
| `created_at`         | str     | ISO date the file was generated.                                                                  |
| `examples`           | list    | List of `n_examples` dicts (per-example schema below).                                            |

Each item in `examples` is a dict with:

| Key                                   | Type        | Description                                                                                            |
|---------------------------------------|-------------|--------------------------------------------------------------------------------------------------------|
| `token_ids`                           | list[int]   | The 21-token input sequence as Pythia BPE ids.                                                         |
| `token_strings`                       | list[str]   | Same sequence as raw BPE pieces (with the `Ġ` prefix on word-starts).                                  |
| `total_len`                           | int         | `21` (no BOS).                                                                                         |
| `positions`                           | dict        | Position spans: `source` `[0,4]`, `target` `5`, `distraction` `[6,15]`, `repetition` `[16,20]`.        |
| `source_token_ids` / `source_token_strings` | list  | The 5 source tokens.                                                                                   |
| `target_token_id` / `target_token_string`   | int / str | The token at position 5 — the one the model must predict at the end.                                   |
| `distractor_token_ids` / `distractor_token_strings` | list | The 10 distractor tokens at positions 6–15.                                                            |
| `prediction`                          | dict        | `position` (20), `target_id`, `target_string`. Convenience field.                                      |
| `example_id`                          | int         | Index within the file.                                                                                 |
| `seed`                                | int         | Per-example random seed derived from `master_seed`.                                                    |
| `token_log_frequencies`               | dict        | Log-frequencies of `source` (list), `target` (scalar), `distraction` (list).                           |

`metadata/<variant>/<draw>/` contains per-draw companion files documenting which tokens were selected from §5 to populate each split, plus generator-side summaries.

## 7. Reverse-LSC and zero-distractor positive controls — `LSC_data/reverse_lsc/`

Two within-task positive-control variants used in the appendix.

| File                                            | Sequence format                  | Purpose                                                                                          |
|-------------------------------------------------|----------------------------------|--------------------------------------------------------------------------------------------------|
| `{train,val,test}.json`                          | `[T][S1..S5][R1..R10][S1..S5]`   | Reverse-copy: target precedes the source prefix; tests whether the LSC mechanism is direction-invariant. |
| `zero_distractor/{train,val,test}.json`         | `[S1..S5][T][S1..S5]`            | Distractor-free copy at a 5-token distance; isolates direct-copy attention from induction.       |

Per-file schema is the same as §6 with the appropriate `task` (`reverse_LSC` / `LSC`), `variant` (`positive_control` / `zero_distractor`), and `sequence_structure` keys. Generator scripts (`generate_reverse_lsc.py`, `generate_zero_distractor_lsc.py`) are committed alongside the data.

## 8. Provenance and regeneration

All files in this repository are deterministic outputs of the data-construction pipeline driven by `master_seed = 42`. To regenerate from scratch, follow stage 1 of the [README reproduction script](README.md#reproducing-the-experiments). Heavy intermediates (activation `.npz` caches, tuned-lens weights, raw Pile shards, pickled token contexts) are not committed; they are listed in [`.gitignore`](.gitignore) and regenerated by stage 2 / stage 3.

The underlying corpora and tokenizer remain the property of their respective authors:

- The Pile (deduplicated subset) — EleutherAI, mixed component licenses; see <https://pile.eleuther.ai/>.
- FineWeb sample — HuggingFace, ODC-By 1.0; see <https://huggingface.co/datasets/HuggingFaceFW/fineweb>.
- Pythia tokenizer / vocabulary — EleutherAI, Apache 2.0; see <https://huggingface.co/EleutherAI/pythia-70m>.
